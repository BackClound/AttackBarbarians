## 1. 文档体系说明

### 1.1 为什么拆分

| 问题 | 解法 |
|------|------|
| 单文档过长，产品/程序/QA 各看各的 | PRD 写「做什么」，SDD 写「怎么做」 |
| 模块细节淹没在总览里 | 每个系统独立 SDD，便于迭代维护 |
| 实现状态难追踪 | 每份 SDD 含「实现状态分析」章节 |

### 1.2 三层结构

```
┌─────────────────────────────────────────────────────────┐
│  Design_document.md (GDD)     玩法意图 · 数值 · 经济规则  │
├─────────────────────────────────────────────────────────┤
│  产品PRD.md (≈20章)           产品需求 · 用户旅程 · 验收   │
├─────────────────────────────────────────────────────────┤
│  docs/sdd/SDD-01~13          分模块系统设计 · 实现分析    │
├─────────────────────────────────────────────────────────┤
│  本文档                       索引 · 追溯 · 维护约定       │
├─────────────────────────────────────────────────────────┤
│  技术规格说明书.md             全局架构 · 数据流 · 测试策略  │
└─────────────────────────────────────────────────────────┘
```

### 1.3 合理 PRD 应包含的内容（本项目映射）

| PRD 标准章节 | 本项目文档位置 |
|-------------|----------------|
| 项目概述 / 卖点 | [产品PRD.md](产品PRD.md) §1 |
| 核心玩法循环 | 产品PRD §2 |
| 玩家 / 战斗 / 技能 | 产品PRD §3–5 + SDD-02~04 |
| Roguelike Buff | 产品PRD §6 + SDD-07 |
| 敌人 / Boss | 产品PRD §7–8 + SDD-05~06 |
| 装备 / 局外成长 | 产品PRD §9–10 + SDD-08~09 |
| 经济 / UI / 音频 | 产品PRD §11–13 + SDD-10~12 |
| 美术 / 数值 | 产品PRD §14–15 + GDD |
| 存档 / 技术 / 商业化 | 产品PRD §16–18 + SDD-01/13 |
| MVP 范围 / 排期 | 产品PRD §19–20 |

### 1.4 SDD 应包含的内容（统一模板）

1. 文档元信息（版本、关联 PRD 章节、实现度）
2. 系统概述与边界
3. 需求追溯（FR/US）
4. 核心类与架构
5. 数据模型 / 配置
6. 流程 / 状态机
7. **实现状态分析**（✅ ⚠️ ❌ 🔜）
8. 已知问题与技术债
9. 测试要点

## 2. 需求归纳方式

### 2.1 双轴归纳

```
产品轴：用户旅程 → 业务域 → 功能点(FR) → 业务规则(BR) → 验收(AC)
工程轴：架构层 L0–L5 → 模块 → 类/服务 → 配置/事件
```

- **PRD** 按用户可感知的业务域写（战斗、成长、经济、UI…）
- **SDD** 按代码模块写（WaveManager、UpgradeCardManager…）
- **追溯矩阵** 连接两者

## 6. 维护约定

1. **新功能**：先改 PRD（FR/AC）→ 改对应 SDD → 更新本页完成度表  
2. **纯重构**：只改 SDD + 技术规格  
3. **数值调整**：改 GDD；影响 AC 时同步 PRD  
4. **ID 不复用**：废弃标 Deprecated
